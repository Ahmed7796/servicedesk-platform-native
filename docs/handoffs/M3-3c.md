## What the whole task does
A `request.submitted` event on `copilot.triage` is parsed, de-duplicated in Redis (`processed:copilot:{eventId}`, 7 days), triaged by the agent (read tools, then one validated `POST /triage` by our code), and marked only after a terminal outcome. Retryable failures are requeued after 1 s then 2 s, counted in Redis (`attempts:copilot:{eventId}`, 1 h), and dead-lettered on the 3rd attempt to `copilot.triage.dlq` via `copilot.dlx`. Bad envelopes go straight to the DLQ (differs from notify on purpose). Rule 6: the only write is the triage post; the consumer only calls `handle`.

## Review fixes (after the lead's E2E run)
- **Readiness race:** aio-pika runs connection callbacks as separate futures. `Consumer` keeps a generation counter (bumped by every loss, reconnect and stop). `_signal_ready` (used by `start`, `_reconnected` and `_retry_ready`) clears the marker again if the generation changed or `stop()` ran while `on_ready` was in flight. Tests: loss during the reconnect ping, stop during the reconnect ping, loss during a retry ping (that one passes by cancellation and is a regression guard), `stop()` twice.
- **Stale marker:** the lifespan clears the marker file before anything starts.
- **Redis timeouts:** `socket_timeout` and `socket_connect_timeout` are 4 s (`REDIS_TIMEOUT_SECONDS`). redis-py 8.1 already defaults `socket_timeout` to 5 s, so the explicit value is 4 s to make the test able to see it is set.
- **httpx:** tests assert `aclose` runs on both the normal and the failure path.
- **Logs:** one INFO line `triage posted for request <uuid>` (agent.py), and `triage attempt N/3 failed for request <uuid>: <fixed reason>, retrying` (handler.py). Ids and fixed reasons only.
- Not done on purpose: the Gemini client is not closed (it has no close).
- Mutations: generation check removed (2 failed), stale-marker clear removed (1 failed), `socket_connect_timeout` removed (1 failed); all restored.

## Operational note
`COPILOT_CONSUMER_ENABLED=false` is for tests and local runs only. In Compose it leaves the container with no marker, so it stays unhealthy and the api (which waits on it) never starts.

## Known limits
- While Redis is down a message loops (requeue, 1 s backoff, repeat) instead of dead-lettering. Accepted for the demo.
- `connect_robust` reconnect and restore of queue, binding and consumer rely on aio-pika and are only tested against fakes. The marker follows its callbacks; nothing re-checks the binding on the broker.
- Redelivery after a lost Redis mark posts again; the API upsert (M1-4b) makes it harmless. Two in-flight copies of an event share one attempts counter.
- An unexpected exception from `deps.triage` is retryable here, non-retryable in `agent.py`'s own catch-all (see `M3-3c-1.md`).
- A message that reaches the DLQ is not read or replayed by anything yet.
