## Decisions made
- **External refs:** hey-api resolved `../events/defs.schema.json#/$defs/...` itself. `@apidevtools/json-schema-ref-parser` was NOT added.
- **`@hey-api/client-fetch` was NOT added.** hey-api 0.99 emits its fetch client into the generated folder (`client/`, `core/`), so there is no runtime import. Only `@hey-api/openapi-ts` 0.99.0 (dev) was added, pinned exactly.
- **No default base URL in generated code:** by default the generator bakes in the contract's `servers` URL (`http://localhost:8080`, the C# API directly). I set `baseUrl: false` on the client plugin, so no runtime default exists. The `ClientOptions` type in `types.gen.ts` still mentions the server URL as a type hint only; it is never used as a value.
- A test asserts both generated clients have no `baseUrl` before `configureApi`, so removing `baseUrl: false` is caught.
- Two generated folders (one per contract) so `/api` and `/notify` clients are separate; both get the same base URL and token.
- `getHealth` is public, so the bearer test uses `listPendingForMe`.
- Auth uses the generator's `auth` callback on the config (reads the token store on each request); no hand-written fetch wrapper.

## Review this hardest
- `getBaseUrl()` default parameter reads `process.env.EXPO_PUBLIC_API_BASE_URL` as a literal so Expo can inline it at bundle time. If someone changes that access to a dynamic form, the variable would silently be undefined on device. I have not run it on a device.
- `App` calls `configureApi` during render (idempotent `setConfig`, but a side effect in render). Moving it to module scope or an effect is possible; I kept it simple.
- Known position labels in `positions.ts` are the five examples from `defs.schema.json`; display wording is my choice.
