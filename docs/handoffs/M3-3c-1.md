## Flow of `handle`
1. Bad envelope: DEAD_LETTER at once. **This differs from notify on purpose**: notify's retry interceptor retried malformed bodies about 3 times before the DLQ; retrying a parse failure cannot help.
2. Type other than `request.submitted` or version other than 1: log, ACK, not marked.
3. `is_processed` then `incr_attempts`. A Redis error here: RETRY (1 s). The check is never skipped.
4. `deps.triage is None`: outcome `skipped`, terminal. Otherwise run it; an unexpected exception (agent catches its own) counts as retryable.
5. Retryable outcome: attempt < 3 gives RETRY with delay 1 s then 2 s; attempt 3 gives DEAD_LETTER, clears the counter, logs one warning `triage retries exhausted for request <uuid> (event <uuid>): <fixed reason>`. Not marked.
6. Terminal (posted, skipped, any non-retryable failure): `mark_processed` after the work, then ACK. If the mark fails after a post: RETRY, or DEAD_LETTER on attempt 3. Once the mark has succeeded, `clear_attempts` is best effort: a failure logs the class name only and still ACKs (the counter expires in 1 h), so an event is never both marked and dead-lettered (review fix; `test_clear_attempts_failure_after_mark_is_best_effort`). The post is an upsert per M1-4b (a second post replaces it, no state change, audit or event); `test_stub_accepts_a_second_post_upsert_itself_rests_on_m1_4b` only shows the client copes with two posts.

## Decisions
- **Terminal outcomes marked:** posted, skipped (no key / no LLM), non-retryable failed (invalid model output, 400/401/403/404 and "request not found").
- **TTLs:** processed 7 days (same as notify); attempts 1 hour.
- **Attempt counting:** a Redis counter, not `x-death`. `x-death` exists only after dead-lettering (a retry via DLX/TTL queues needs two more queues) and its shape is broker-dependent; `redelivered` is a boolean. The counter works with the Redis we already need, survives a consumer restart, and is testable with the same fake store.
- The consumer (PR 2) sleeps `delay_seconds` then requeues. That sleep must be cancellable on shutdown (requested; PR 2).
- DLQ messages are not marked and their counter is cleared, so a replay starts fresh.

## Known limits (state these in the PR)
- An unexpected exception from `deps.triage` is treated as retryable here, while `agent.py`'s own catch-all treats it as non-retryable. Reason: agent.py's catch-all covers model/SDK faults where a retry rarely helps and the advisory result is optional; at this outer layer the exception is something we did not foresee (for example a bug or a transient fault), so a bounded 3 attempts then the DLQ keeps the message visible instead of silently marking it done.
- The envelope is looser than the schema on `occurredAt` (Pydantic's lax datetime accepts forms RFC 3339 does not) and on UUID forms (`UUID()` accepts braces, URN and no-hyphen forms). Accepted for a lenient consumer; ids are normalised to the hyphenated form.
- Two in-flight copies of the same event share one attempts counter, so they can use up attempts faster. A small gap; the upsert makes a double post harmless.
- **While Redis is down, a message loops** (requeue, then a 1 s backoff, repeat) instead of dead-lettering, because neither the check nor the counter can be read. Accepted for the demo.
- Requeue puts the message back at the head of the queue; with prefetch small and one consumer a retrying message delays the others by the backoff.
- Unsupported type/version events are acked unmarked.
- If Redis applies the mark but its reply is lost (a timeout after the write), the handler sees a failed mark: on attempt 3 the event is then both marked and dead-lettered, and a DLQ replay is acked as a duplicate. Undetectable from the client; accepted (reviewer, second pass).
