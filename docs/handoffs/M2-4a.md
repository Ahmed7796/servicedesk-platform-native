# Hand-off: M2-4a devices endpoint, PushSender, push on events

**Agent:** notify-spring  **Date:** 2026-11-18

Part 1 of M2-4. The overdue job (`overdue_since`, scheduled push) is M2-4b and is not started.

## What changed
- `db/migration/V3__device.sql`: table `device` (PK `expo_push_token`; `user_id`, `platform`, `roles text[]`, `updated_at`), index on `user_id`. M2-4b's migration becomes V4.
- `push/DeviceController` + `DeviceRegistration`: `POST /notify/devices`, 204. `@PreAuthorize("!hasRole('TriageService')")`; the body is validated inside the method, so a service token with a valid JSON body always gets 403. Malformed JSON fails body parsing before the role check and gets 400; nothing is written either way, and the contract does not fix the order. Stores the caller's JWT roles with the token.
- `push/ProblemAdvice`: `ResponseEntityExceptionHandler` so 400s are `application/problem+json` (the contract's `ProblemDetails`).
- `push/DeviceRepository`: upsert on the token (a token moves to the latest user), tokens by user ids, tokens by role, delete.
- `push/PushSender` (interface), `PushMessage`, `PushResult` (OK / INVALID_TOKEN / FAILED), `push/ExpoPushSender` (RestClient over the JDK HTTP client, 5 s timeout, never throws, maps `DeviceNotRegistered` to INVALID_TOKEN).
- `push/PushNotifier`: picks recipients, sends, deletes invalid tokens. Never throws. `push/PendingNotice`: record handed from the handler.
- `events/ProjectionHandler.handle` now returns `Optional<PendingNotice>` (present only when a row was written for `request.submitted` or `request.step_approved`). `PendingStepRepository.upsertSubmitted` returns the row count; new `titleOf`.
- `events/EventListener`: after `handle` commits, calls the notifier, then marks Redis.
- `application.yml`: `app.notify.push.enabled`, `app.notify.push.url`.
- Tests: `DeviceEndpointTest`, `PushNotifierTest`, `ExpoPushSenderTest`, `FakePushSender`; `EventListenerTest` constructor updated and 5 tests added. No dependency added, `pom.xml` untouched. About 860 lines including tests (main code roughly 330).

## Decisions made
- **Strict body by hand** (what I used instead of the annotation): the controller takes the raw `JsonNode` and `DeviceRegistration.problem()` checks unknown keys, token pattern, platform enum and types. Reason: the annotation does not work, there is no Bean Validation starter (no new dependency), and the global Jackson setting and lenient event parsing stay untouched. Alternatives: a dedicated strict ObjectMapper; `@JsonAnySetter`.
- **Push after commit, outside the transaction, before the Redis mark, gated on "a row was written".** A replay returns empty and never pushes, and Redis de-dup stops ordinary repeats. Cost: a crash between commit and push loses that push (at most once). A push failure never fails the event or touches the projection. Alternative: push inside `handle`, rejected (network call in a transaction, failure could roll back).
- **Unassigned step goes to devices whose stored roles contain `Admin`** (roles saved at registration from the JWT), because this service has no user directory. Limits: only admins who have opened the app and registered get it; roles are as of the last registration, so a demoted admin keeps getting these pushes until the token is registered again by someone else; an Admin who registered while also being an approver is still found by role.
- A token registered by another user is moved to that user (and takes their roles), per the contract.
- Logs: request id and counts only. No token, no title (`logsNeverContainATokenOrTheRequestTitle` checks it). The push body does contain the title (sent to the phone).
- Failed pushes are not retried; the 4b overdue push is the safety net.

## Review this hardest
- `ProjectionHandler.submitted` / `stepApproved`: the "row was written" result decides whether anyone is pushed. A wrong guard means duplicate or missing pushes.
- `EventListener.onMessage` ordering: handle (commits), notify, then mark.
- `DeviceController`: 403 before any body validation, and `DeviceRegistration.problem` against the contract.
- `ExpoPushSender.interpret`: I could not call real Expo; the response shape (`data` object or array, `details.error = DeviceNotRegistered`) is from Expo's documented format, tested only against a fake.

## Known limits
- Any signed-in user can register another user's token if they learn it. That user's approval pushes then go astray (denial of service), but nothing leaks: delivery goes to the device that owns the token, and roles come from the registrant's own JWT. Acceptable for the demo.
- `app.notify.push.enabled=false` in `application-pipeline.yml`, so no test can call exp.host.
