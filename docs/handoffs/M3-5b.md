**Agent:** copilot-python  **Date:** 2026-11-19

## What changed (under `triage-copilot/`)
- `app/ratelimit.py` (new): `RateLimiter(per_minute, clock=time.monotonic)`, a sliding 60 s window; `try_acquire()` returns a bool and a refused call changes nothing. Rejects a limit outside 1..1000.
- `app/agent.py`: `triage(..., limiter=None)`. The token is taken once per run, after the id and key checks and before the first LLM call, and never in canned mode. When refused: non-retryable `skipped` "rate limited, nothing posted". After validation, `confidence < COPILOT_MIN_CONFIDENCE` gives non-retryable `skipped` "low confidence, nothing posted" (no value logged; invalid output is still `failed` first).
- `app/config.py`: `copilot_min_confidence` and `copilot_rate_limit_per_minute`. Bad values stop startup through the 5a `ConfigError` path, naming only the variable.
- `app/main.py`: one `RateLimiter` per process is created in the lifespan and passed to every `triage()` call.
- `README.md`: two variable rows.
- Handler, consumer and M3-3c code are unchanged. Both skips are terminal, so the real handler marks and acks them (tested); no attempt is retried, nothing reaches the DLQ.

## Decisions made
- Sliding window rather than a refilling bucket: simpler to explain and test, same burst protection.
- Per-run, not per-LLM-call, because one request costs one unit of demo budget.
- A refused call does not extend the window.

## Review this hardest

- `ratelimit.py` boundary (`>= 60 s` frees a token).

## Known limits
- The phone cannot tell "pending" from "skipped": a low-confidence or rate-limited request shows "No suggestion yet" (M4-3a), the same as one not yet triaged.
- The rate limit is per process (in memory, resets on restart). A Redis counter is the follow-up if the copilot is ever scaled out.
- A rate-limited request is never triaged unless replayed. Option A (a retryable outcome that does not use up the attempt counter, needing a small handler change) is a possible later task.
- Every retry takes another token, so a retryable failure whose retry hits the limit is dropped for good (no suggestion). The lead saw this live with the limit at 1: request A took the token, Gemini answered 503, the retry hit the limit and became a terminal "rate limited, nothing posted"; request B was limited at once; both stayed Submitted and the DLQ was empty. This follows from Option B; Option A, or "don't charge retries", is the later fix.
- If an operator sets `COPILOT_MIN_CONFIDENCE` above 0.7, canned suggestions are skipped too (by design, same rule).
