## Decisions made
- `popTo` alone is wrong when no RequestDetail exists. React Navigation 7 then replaces the current screen, so a tap on PendingApprovals ended with only [RequestDetail] (my first version, caught by the real-navigator test). Hence three branches above.
- Signed out (or token unreadable): reset to Login and drop the link, as agreed. The token is read at tap time, not at app start, so a sign-out or sign-in after launch is respected.
- Foreground refresh requires a valid `requestId`, and only fires on PendingApprovals. On RequestDetail nothing happens, even for the same request (no detail refetch).
- A cold-start response with an invalid id is marked handled and ignored.

## Review this hardest
- `openRequest`: the token read is async, so a second tap can interleave; both end in the same single-entry state, but there is no lock.
- The cold-start path expects `navigationRef.isReady()` to be true when the effect runs after `signedIn` resolves. That order is fixed by React, not by timing: children's passive effects run before the parent's in the commit that mounts `Stack.Navigator`. If the hook ever moves and the ref is not ready, the tap now waits for the next `state` event instead of being lost (tested with `isReady` forced false). The only remaining unknown is how expo-notifications reports a killed-app tap on a real device.
- `handled` is module state, so tests need distinct identifiers (they use them).
- Not checked on a device: Android cold start from a killed app (docs say Android uses a JS task there in some cases), and the banner look.
