# Hand-off: M1-5a Audit entry Sequence (domain, configuration, migration)

**Agent:** api-dotnet  **Date:** 2026-11-18

## What changed
- `AuditLog` (Domain): new `int Sequence`, a constructor parameter.
- `ServiceRequest` (Domain): one private helper `AppendAudit(...)` is now the only place an audit entry is created. It sets `Sequence = _auditLogs.Count + 1`. All six former `_auditLogs.Add(new AuditLog(...))` sites (Submit x2, Approve, Reject, Cancel, Fulfil) call it. No behaviour change otherwise.
- `AuditLogConfiguration`: the plain index on `ServiceRequestId` is replaced by a unique index on (`ServiceRequestId`, `Sequence`); it still serves lookups by `ServiceRequestId` alone.
- Migration `AddAuditLogSequence` (generated, plus hand-written SQL): adds `Sequence integer NOT NULL`, backfills existing rows with `ROW_NUMBER() OVER (PARTITION BY "ServiceRequestId" ORDER BY "OccurredAt", CASE WHEN "Action" = 'Submitted' THEN 0 ELSE 1 END, "Id")` (`Action` is stored as a string, per `AuditLogConfiguration`), then creates the unique index. Model snapshot updated. No committed migration was edited.
- Not in the API: `Sequence` is not exposed. No DTO, service or controller change (that is M1-5b). No seeder change (dropped by decision).

## How it was verified
- `dotnet test ServiceDesk.slnx`: before 332 passed; after 340 passed (8 new), 0 failed.
- New tests, `tests/ServiceDesk.Tests/Domain/AuditSequenceTests.cs`: Submit gives 1; escalated Submit gives Submitted=1 and StepEscalated=2 with equal `OccurredAt`; Approve after that gives 3; a full flow (submit, two approves, fulfil) gives 1..5; Reject and Cancel append next; a failed Approve (asserted as `ApprovalNotAllowedException`) consumes no number; the EF model has the unique (`ServiceRequestId`, `Sequence`) index (model-only, no database).
- Mutation check, restored afterwards: `Count + 1` changed to `Count` made 7 tests fail.
- NOT verified by tests: the migration SQL (backfill and index creation). There are no database tests, so the lead proves it in compose against a database that already has audit rows. Check that the first migration run on existing data does not fail on the unique index.
- Load paths leading to a state change: every `ServiceRequestService` method that changes a request loads it only through `IServiceRequestRepository.GetByIdAsync`, which does `.Include(r => r.AuditLogs)`. The other repository reads (`ListAsync`, `ListPendingCandidatesAsync`, `ExistsAsync`) are `AsNoTracking` and are used for reads only; none of them feeds a state change. `TriageSuggestionService` changes nothing on the request.

## Decisions made
- Domain-assigned `Sequence`, not a PostgreSQL identity, because EF orders INSERT commands within a table by key, so same-millisecond v7 keys could insert in random order. Alternative considered: identity column; ordering by action rank.
- Concurrency: two writers cannot both append number N, because the request's `xmin` concurrency check makes the loser fail; the unique index is a backstop.
- The migration file was saved without the generator's BOM and with LF; the other migrations were not touched.

## Review this hardest
- `ServiceRequest.AppendAudit`: correctness depends on `_auditLogs` holding all existing entries. A future load path that skips `Include(AuditLogs)` would produce duplicate numbers, and the unique index would turn that into a failed save rather than bad data.
- The hand-written backfill SQL in the migration (quoting, the `UPDATE ... FROM` join, the `ORDER BY`). The reviewer caught the original order: `"OccurredAt", "Id"` would sort a Submitted/StepEscalated pair at random, because both v7 Ids fall in the same millisecond. The `CASE` puts `Submitted` first on a timestamp tie.
- Backfill limit: one Submit escalates a step only when the requester's position equals that step's position. Every seeded template uses each position once and a requester has one position, so one Submit writes at most one StepEscalated. But the domain does not forbid a template that repeats a position, so in theory several StepEscalated rows could tie; their order for pre-migration rows would then not be guaranteed (ordered by `Id`). Accepted for demo data; `Details` is not parsed.

## Java to C# notes
- `private void AppendAudit(...)` as the single creation point is like a private method in a JPA aggregate root that all state-changing methods call; the difference is that the child list is a private `List<AuditLog>` field that EF fills through the field (`PropertyAccessMode.Field`), not a getter.
- `_auditLogs.Count + 1` is like `auditLogs.size() + 1` on a Hibernate `@OneToMany` list; the difference is that it is only correct if the collection was fully loaded (`Include`), where Hibernate would lazy-load it silently.
- `HasIndex(l => new { l.ServiceRequestId, l.Sequence }).IsUnique()` is like `@Table(uniqueConstraints = @UniqueConstraint(columnNames = {...}))`; the difference is that it is configured in the fluent `IEntityTypeConfiguration`, not with annotations on the entity.
- A migration (`Up` and `Down`, with `migrationBuilder.Sql(...)`) is like a Flyway or Liquibase changeset; the difference is that EF generates the schema part from the model diff and you hand-edit it for data steps such as this backfill.
- `Assert.Equal([1, 2, 3], Sequences(request))` uses a C# collection expression, like `List.of(1, 2, 3)` in an AssertJ `containsExactly`.
