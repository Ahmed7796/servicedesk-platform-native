## Decisions made
- Uniqueness of `approverUserIds`: the schema says `uniqueItems`. Before this task nothing in code enforced it; it relied on the repository returning each user once (true for the real query, since Id is the primary key). The resolver now calls `.Distinct()` on the ids, so the guarantee sits where the list is made. Alternative: dedupe in the service or factory, further from the source.
- Last-step decision uses `request.Status == Approved` (what the domain decided and what the event reports), not a second look at the steps.
- Admin as actor: when the requester holds the step's position (GeneralManager requester on a GM step), the Admin decides; `actorId` is the Admin's id. A DepartmentHead requester is escalated to GM and is not this case. Because that workflow has one step, the event is `request.approved`.
- `request.cancelled.previousStatus` can only be Submitted or InReview: `Cancel` throws before any change unless the state machine allows Cancel, and it allows it only from those two. Tests: cancel from both statuses with the payload checked, and cancel from Approved, Rejected, Cancelled and Fulfilled each throw with no row added.
- Cancel's `previousStatus` and the decided step are read before the domain call (the domain call changes both).

## Review this hardest
- Mutation 4 survived and is an equivalent mutant: `ApproverResolver` returns `[]` when the request has no pending step, without touching the repository, so calling it on the final approve is invisible to any test (the class is `sealed`, so I cannot spy on the resolver itself). `ApproveLast_DoesNotCallTheResolver` therefore documents the intent, and the real protection is that taking the wrong branch fails (the extra mutation, 3 failed). Say if you want the resolver behind an interface to make it spy-able; I did not, to keep the diff small.
- Concurrency conflict: the unit test `Save_ConcurrencyConflict_PropagatesAfterOneAdd` shows only that the row was added once and `ConcurrencyConflictException` reaches the caller. The rollback itself is SQL Server's job (a failed `UPDATE ... WHERE RowVersion = @old` rolls back the whole SaveChanges batch, including the INSERT into `OutboxMessages`). Not tested here.
- In `ApproveAsync`, if the resolver throws after `request.Approve` the in-memory entity is already changed. Nothing is saved because the exception propagates and the scoped context is discarded with the HTTP request. Same as every other domain throw, not new, but worth a look.
- `ServiceRequestService` methods now have more steps each; check the order in Approve most carefully.

## Java to C# notes (C# tasks only)
- Primary constructor `class ServiceRequestService(IServiceRequestRepository requests, ..., IOutboxRepository outbox, ApproverResolver approvers, ...)` is like Spring constructor injection with `final` fields and no `@Autowired`; the parameters are captured and usable in every method, but are not fields you can name with `this.`. Differences: DI container is `services.AddScoped<>()`, not component scanning.
- `AddScoped<IOutboxRepository, OutboxRepository>()` is like a `@Repository` bean in request scope (one per HTTP request). The same scoped `AppDbContext` is shared by all repositories, so one `SaveChangesAsync` is the unit of work: it is like one `@Transactional` boundary, but there is no annotation. EF wraps the whole save in a single database transaction.
- `Substitute.For<T>()` (NSubstitute) is like Mockito `mock()`; `Received(1)` is `verify(times(1))`, `DidNotReceive()` is `verify(never())`; `When(...).Do(...)` is like `doAnswer`.
- `[Theory]` with `[InlineData(...)]` is like JUnit 5 `@ParameterizedTest` with `@CsvSource`/`@EnumSource`; enum values in `InlineData` work because the enum is public.
- `Record.ExceptionAsync` returns the thrown exception (or null) instead of asserting, like capturing with `assertThrows` but letting me check the type afterwards with `Assert.IsType` (exact type, not subclasses, unlike `assertThrows`).
- `.Distinct()` and `.Order()` are LINQ, like `stream().distinct().sorted()`; LINQ is lazy until `ToList()`, like a stream until a terminal operation.
- `JsonDocument.Parse(...).RootElement` is like Jackson's `JsonNode` read-only tree; `GetProperty("x")` throws if the key is missing, which is useful in tests.
- `request.CurrentStep!` : the `!` tells the compiler the value is not null (no Java equivalent; it is a promise, not a check).
