## Adapter details (verified from the RabbitMQ.Client main-branch docs via Context7, not against a live broker)
- Confirms: `CreateChannelAsync(new CreateChannelOptions(publisherConfirmationsEnabled: true, publisherConfirmationTrackingEnabled: true))`. With tracking on, `BasicPublishAsync` completes only when the broker acks and throws `PublishException` on a nack. There is no `WaitForConfirmsAsync` in 7.x. The client has no confirm timeout, so a linked `CancelAfter(10 s)` token is used.
- Properties: `ContentType = application/json`, `MessageId = row.Id.ToString()`, `Type = row.Type`, `DeliveryMode = Persistent` (2). Routing key = `row.Type`; body = `Encoding.UTF8.GetBytes(row.Body)`. `mandatory: false`, so a message with no bound queue is acked and dropped (as the contract says).
- `message_id` equals the envelope `eventId` text: the factory serialises the same `Guid` with System.Text.Json, which writes the lowercase hyphenated "D" form, identical to `Guid.ToString()`. The lead compares them in compose.
- Failure mapping:
  - `PublishException` becomes `PublishRejectedException`; the channel is kept.
  - `OperationCanceledException` while the caller's token is cancelled is rethrown (shutdown).
  - Everything else caught becomes `BrokerUnavailableException` and the channel and connection are discarded: `OperationCanceledException` (confirm timeout), `IOException` (includes `BrokerUnreachableException` at connect time), `SocketException`, `RabbitMQClientException` (base of `AlreadyClosedException`, `OperationInterruptedException` and `PublishException`, which is caught first), `TimeoutException`, `ObjectDisposedException`.
  - Not checked at runtime: that `BrokerUnreachableException` is an `IOException` (from the 7.x source); the compose "RabbitMQ down" test covers it.

## Decisions made
- Exchange declared on each new connection, not at startup, because the contract was updated for that (consumers declare it too). Alternative: a startup hosted service that connects once.
- Probe lives in the Api project as a separate class with an injectable handler, because `Program.cs` top-level statements cannot be unit tested. Alternative: inline in `Program.cs`, untested.
- `/health` stays DB-only: the outbox buffers while the broker is down, so a broker outage must not mark the API unhealthy.
- Publisher runs in every environment; the outbox is not demo data.
- Rejected rows are skipped and retried next batch (Ahmed's decision, no parking).

## Review this hardest
- `RabbitMqEventBroker`: nothing unit-tests it. Check the catch order (`PublishException` first, shutdown cancellation second, everything else last), that a nack keeps the channel while other failures discard it, and the semaphore (released in `finally`).
- `Program.cs`: the probe line runs before the builder; `return 0` after `RunAsync`.

## Java to C# notes (C# tasks only)
- `BackgroundService.ExecuteAsync` is like a Spring `SmartLifecycle` bean running its own loop thread, not like `@Scheduled`. `@Scheduled(fixedDelay)` cannot do variable backoff or "repeat immediately"; here the loop decides each wait. The host cancels the `stoppingToken` on shutdown, like `SmartLifecycle.stop()`, but cancellation only takes effect where code checks the token or awaits with it.
- `IServiceScopeFactory.CreateAsyncScope()` is like opening a new request/transaction scope by hand. The hosted service is a singleton and `AppDbContext` is scoped, so the loop must create a scope per pass to get a fresh context (injecting the context directly would fail or leak one context for the app's lifetime). Spring avoids this because a `@Transactional` bean call gets a new EntityManager per transaction.
- `await using var scope = ...` is try-with-resources for async disposables; the scope disposes at the end of the enclosing block (the loop body).
- RabbitMQ.Client confirms versus Spring AMQP: with `CorrelationData` you send, then wait on `correlationData.getFuture()` for ack/nack. In RabbitMQ.Client 7 with confirmation tracking enabled, `await BasicPublishAsync(...)` itself is that wait; an ack returns normally and a nack throws `PublishException`. There is no separate callback to wire. `IChannel` is not thread-safe for concurrent publishes, hence the `SemaphoreSlim` (like a `ReentrantLock` around `RabbitTemplate` use on a dedicated channel).
- `SemaphoreSlim(1,1)` with `WaitAsync`/`Release` in `finally` is an async-friendly mutex. A `synchronized` block cannot contain `await`.
- Top-level statements: `Program.cs` is the body of an implicit `static async Task<int> Main(string[] args)`. A bare `return exitCode;` at the top ends the process before the host is built, like `System.exit(code)` before `SpringApplication.run`. Once any path returns an int, all paths must (hence `return 0;` at the end). `args` is the Java `main` argument array.
- `protected virtual Task DelayAsync(...)` overridden in a test subclass is the same trick as a Mockito `spy`/anonymous subclass overriding a protected method. C# methods are non-virtual by default (the opposite of Java), so `virtual` must be written.
- `x is { } probeExitCode` is a pattern match: "not null, and bind it to a variable". For `int?` it unwraps to an `int`. Java 21 has `instanceof` patterns, but not for null checks like this.
- `catch (Exception ex) when (ex is A or B)` is a catch with a filter. Java has multi-catch (`catch (A | B e)`) but no condition on the catch; the C# filter runs before the stack unwinds. `catch (OperationCanceledException) when (ct.IsCancellationRequested)` distinguishes shutdown from a timeout that throws the same exception type.
- `primary constructor` on a `class` (`RabbitMqEventBroker(RabbitMqOptions options, ILogger<...> logger)`) captures parameters for use in all methods; it is not a field named `this.options`. Same as M1-2a.
- `TaskCompletionSource` in the test harness is a `CompletableFuture` you complete by hand.
