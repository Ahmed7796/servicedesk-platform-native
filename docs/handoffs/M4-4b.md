**Agent:** mobile-rn  **Date:** 2026-11-18

## What changed
- `mobile/src/api/decisionErrors.ts`: `decisionErrorMessage(status)`. 403, 409, 400, 404, network (status undefined) and "anything else" have plain texts. 401 returns `null` (no text; the API interceptor owns it). The 403 text names no reason because its body may be empty.
- `mobile/src/screens/useDecision.ts`: `approve(comment)` and `reject(reason)`. An `inFlight` ref (as in LoginScreen) lets only one call through; `submitting` disables the buttons. Approve sends `{ comment }` (trimmed) or `{}`; Reject sends `{ reason }` (trimmed) and does nothing for a blank reason. On success it calls `onDone`; on 409 it also awaits `reload`.
- `mobile/src/components/DecisionPanel.tsx`: one "Comment or reason" box (maxLength 500), Approve and Reject buttons. Reject is disabled while the trimmed text is empty.
- `mobile/src/screens/RequestDetailScreen.tsx`: shows the panel only when `status` is `Submitted` or `InReview` and a step has `decision === 'Pending'` (`canDecide`). The decision error text is rendered by the screen, outside the panel, so it stays visible after a 409 refetch hides the panel. `onDone` runs `navigation.popTo('PendingApprovals', { refresh: Date.now() })`. (Review fix: plain `navigate` pushed a second PendingApprovals in React Navigation 7, so the refresh effect never fired and Back showed a stale detail. `popTo` exists in the installed routers' types and is used with no cast.)
- `mobile/src/navigation/types.ts`: `PendingApprovals: { refresh?: number } | undefined`.
- `mobile/src/screens/PendingApprovalsScreen.tsx`: reloads when `route.params.refresh` changes (not on first render, not for the same value).
- Tests: new `__tests__/RequestDecision.test.tsx` (24) and `__tests__/decisionErrors.test.ts` (8), 1 in `PendingApprovalsScreen.test.tsx`, and 1 in `__tests__/DecisionNavigation.test.tsx`. The screen tests now assert `popTo`. Fixtures use `satisfies` (`ApprovalStep`, `ServiceRequestDetail`, `ServiceRequest`, `ApproveRequest`, `RejectRequest`); fetch is mocked.
- No dependency added. Nothing outside `mobile/` changed except this file. `docs/build-log.md` untouched (lead owns it).

## Decisions made
- Statuses come from the contract's enum: `RequestStatus = 'Submitted' | 'InReview' | 'Approved' | 'Rejected' | 'Fulfilled' | 'Cancelled'`. Buttons show for the first two; the tests hide them for the other four.
- 409 text: "Someone else has acted on this request, or it changed. Showing the latest." It does not promise the refetch worked. If the refetch fails, `useRequestDetail` sets its own error and keeps the old detail on screen, so both messages show (tested).
- One shared text box (approved). Trimmed for both.
- Success keeps `submitting` true until the screen is left, so no second tap is possible while navigating.
- A 401 shows nothing and does not navigate; buttons re-enable (tested).

## Review this hardest
- `useDecision.send`: the flow on success, 409 and 401, and `succeeded` leaving the buttons disabled after success.
- Double-submit test: all three presses run inside one `act()`, otherwise React re-renders between them and the disabled button would hide a missing ref guard (the mutation confirms it catches it).
- `canDecide` is a client-side guess (no contract field). A user who is not the right approver still sees the buttons and gets a 403 message.
- After a success the detail screen is not refetched; the list reloads instead via `refresh`. If the user goes Back to the stale detail, they could see old buttons; the server would answer 409.
- Text colour, layout and the multiline input were not looked at on a screen.
