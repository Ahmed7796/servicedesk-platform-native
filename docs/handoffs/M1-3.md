## Decisions made
- Eligibility is only `CanDecideCurrentStep`; the repository filter is a superset. Alternative: a second SQL copy of the rules (rejected: two rules can drift).
- Role list on the endpoint rather than a policy because M1-4a's `TriageService` is then excluded without touching this endpoint.
- Sorting happens in the service, not in SQL, so the test (which has no database) covers it.
- Requester names come from one `ListByIdsAsync`, because `ServiceRequest` has no Requester navigation and I did not change the model.

## Review this hardest
- `ServiceRequestRepository.ListPendingCandidatesAsync` and `UserRepository.ListByIdsAsync` are UNTESTED (no database provider in the test project). Why each `Where` is a superset:
  - Status Submitted/InReview and `RequesterId != caller`: `CanDecideCurrentStep` rejects finished requests and own requests anyway, so nothing eligible is removed.
  - Approver branch: some step is `Pending` with `Position == caller.Position`. The current step is the lowest-order pending step, so it is always among the pending steps; an eligible approver must hold its `Position`. An escalated step is stored with `Position = GeneralManager` (the original is in `EscalatedFrom`), so it matches the GM and not the original holder. Department scope is not filtered in SQL.
  - Admin branch: `RequesterPosition != null`. The Admin fallback needs `RequesterPosition == step.Position`, which cannot hold when the snapshot is null. Admins are otherwise eligible for nothing, so this branch is the only way an Admin gets rows.
- Mutation 4 (Admin branch returning nothing) is NOT caught by the unit tests, because the fake repository returns every request. It needs the compose check: as the Admin, submit a request as the GM through a workflow with a GM step (none is seeded) or confirm the list is empty and the query runs without error.
- Rows loaded: Approver, all open non-own requests with a pending step at their position (including other departments); Admin, all open requests from approver requesters. No paging, as the contract has none. It grows linearly with open requests, fine at demo scale; the fix would be to push department and scope into SQL or add paging.

## Known limits

This cannot happen today: `ServiceRequestConfiguration` has a Restrict foreign key to Users, so a user with requests cannot be deleted. If that FK ever changes, handle the missing name.

## Java to C# notes (C# tasks only)
- `[Authorize(Roles = "Requester,Approver,Admin")]` is like `@PreAuthorize("hasAnyRole('REQUESTER','APPROVER','ADMIN')")`; the string is a comma-separated list of role claim values, matched case-sensitively, and there is no `ROLE_` prefix.
- `sealed record PendingItemDto(...)` is like a Java `record`; same immutability, and the property names become camelCase JSON through ASP.NET's serializer defaults.
- `object? Triage` is like `Object triage` that may be null; the `?` is a compiler nullability annotation, not a runtime type. Null properties are still written as `null` by default.
- `throw new NotFoundException(...)` after `??` is like `Optional.orElseThrow(...)`; the `??` operator returns the left side unless it is null.
- `candidates.Where(...).OrderBy(...).ThenBy(...).ToList()` is a Java Stream `filter/sorted(Comparator.thenComparing)/toList`. On `IQueryable` (in the repository) the same calls are translated to SQL, like a Spring Data query; on in-memory lists they run directly.
- `db.Users.Where(u => idList.Contains(u.Id))` becomes `WHERE Id IN (...)`, like a JPQL `IN :ids`.
- `AsNoTracking()` is like a read-only Hibernate query without managed entities: no change tracking, cheaper for lists.
- `return [];` is a collection expression for an empty list, like `List.of()`.
