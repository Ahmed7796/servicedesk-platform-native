# Hand-off: M4-2b Stored-token start and 401 session handling

**Agent:** mobile-rn  **Date:** 2026-11-18

## What changed
- `mobile/src/navigation/RootNavigator.tsx`: reads `tokenStore.get()` once; renders nothing until it resolves; initial route is PendingApprovals with a token, else Login. A rejected read counts as "no token".
- `mobile/src/auth/session.ts` (new): `navigationRef` and `handleUnauthorized(failedToken)`. If the stored token equals the token the failed request was sent with, clear it and reset the stack to Login. Parallel calls share one in-flight run.
- `mobile/src/api/config.ts`: `configureApi(baseUrl, getToken, onUnauthorized?)` installs a response interceptor on both generated clients (servicedesk and notification). It fires on any 401 except the login request (matched on the path `/api/auth/login`), passing the request's bearer token from its `Authorization` header. Calling `configureApi` again ejects the previous interceptor first, so renders do not stack handlers.
- `mobile/App.tsx`: passes `handleUnauthorized` and attaches `navigationRef` to the `NavigationContainer`.
- Tests: `mobile/__tests__/session.test.ts` (6 new), `RootNavigator.test.tsx` (4 new, 2 adjusted to wait for the async read), `App.test.tsx` (secure-store mock now has `getItemAsync`; login assertion uses `findByTestId`). No assertion was weakened.
- No dependency added. No refresh attempt: the API has no refresh endpoint, so a 401 means sign in again.

## Decisions made
- Idempotence comes from two things: parallel 401s share one promise, and a later 401 ends the session only if its request was sent with the token still stored. A stale 401 (no token stored, or a different, newer token after signing in again) does nothing. No "signed in again" latch, so `LoginScreen` is unchanged. A 401 on a request sent without a token does nothing.
- Interceptor awaits the handler, so a failing call returns after the token is cleared. Alternative: fire and forget; rejected because ordering in tests and in the UI would be racy.
- The login request is recognised by path suffix, not by operation id, because the response interceptor only receives `Response` and `Request`.
- Mocking `navigationRef.isReady`/`reset` with spies in `session.test.ts` rather than mounting a navigator: the reset call and its argument are the contract; the navigator test covers the initial route.
- The throwing-`replace` test in `LoginScreen.test.tsx` already uses `mockReset` in `beforeEach` plus `mockImplementationOnce` (lead's change); I left it.

## Review this hardest
- `endSession` in `session.ts`: the `??=` shared promise and the `stored !== failedToken` check. If a different-token 401 arrives while a run is in flight, it joins that run and is ignored, which is fine because the run was for the older session.
- `RootNavigator` returns `null` while the token read is pending. If secure storage hangs, the app stays blank; there is no timeout.
- `isLoginRequest` uses `new URL(request.url).pathname.endsWith('/api/auth/login')`. A base URL with a path prefix still matches; a renamed login path would silently make wrong passwords log the user out (the test would catch the rename only if the contract and generated client change).
- `App` still calls `configureApi` during render (from M4-1b); the eject makes that safe, but it is still a side effect in render.
