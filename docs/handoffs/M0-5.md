## Decisions made
- Added a ProjectReference from ServiceDesk.Tests to ServiceDesk.Infrastructure because `AddInfrastructure` lives there and the test project only referenced Domain and Application. No NuGet package was needed. Alternative considered: testing through the whole host, which is heavier.
- Blank or whitespace counts as missing because an empty env var would otherwise produce a confusing SQL error later.
- No README change, as agreed: the error message and `.env.example` cover the setup.

## Java to C# notes (C# tasks only)
- `ConnectionStrings__Default` env var is like Spring relaxed binding (`SPRING_DATASOURCE_URL`); .NET maps `__` to the `:` section separator, so it becomes `ConnectionStrings:Default`.
- `dotnet user-secrets` with `UserSecretsId` is like a git-ignored `application-local.properties` kept outside the repo; it is only loaded in Development, unlike a Spring profile file which is selected by profile name.
- `appsettings.Development.json` is like `application-dev.yml`, layered over `appsettings.json` by environment name.
- `ProjectReference` is like a Maven module `<dependency>` on a sibling module; the difference is that it points at a `.csproj` path, not coordinates, and is built from source in the same solution.
- `IConfiguration` / `AddInMemoryCollection` in the test is like building a `MockEnvironment` or `@TestPropertySource` so the code runs without starting the Spring context.
- `Assert.Throws<T>` is like JUnit `assertThrows`; `[Theory]` with `[InlineData]` is like `@ParameterizedTest` with `@ValueSource`.
- `string.IsNullOrWhiteSpace` is like `StringUtils.isBlank`.
