## Decisions made
- The overdue call is fire-and-forget under the request counter, so a slow or dead `/notify` never delays the list. Consequence: badges can appear a moment after rows.
- A failed overdue refresh clears the badges (empty set) instead of keeping stale ones, as agreed.
- `signOut` retries once, then resets to Login even if clearing still fails, with a visible notice (route param, no new screen). In that rare case the token can survive and the next start would open PendingApprovals, but the user was told.
- Only the API ends a session on 401 (rule 7: it issues the token). If the token is truly expired, the pending-for-me call gets 401 too.
- Matching ignores `assignedUserIds`: the server already scopes the list to the caller.

## Review this hardest
- `usePendingApprovals.load`: the overdue promise chain starts before the pending `await`; both check `current()`. A change to the order could let the overdue result for an older request apply.
- `signOut`: the retry loop and that the reset always runs; the unhandled-rejection test relies on the button calling it with `void`.
- A 401 arriving after sign-out finds no token and does nothing, and a notification-service 401 never reaches the handler.
- The badge colour (#b00020 on white text) and the label were chosen without a contrast check.
