## Decisions made
- **Retry property.** Boot 4 has no `max-attempts` for listener retry; it is `spring.rabbitmq.listener.simple.retry.max-retries` (a wrong key is silently ignored and the default gave 4 attempts; a test caught it). Set to 2, so 1 try + 2 retries = 3 attempts, then rejected without requeue (`default-requeue-rejected: false`) to the DLQ. Backoff 1s x2 in the service; 100ms in tests.
- **Malformed body** (unparseable, or no eventId, type, requestId or occurredAt): `AmqpRejectAndDontRequeueException` straight to the DLQ. It still goes through the retry interceptor, so it takes about 3 attempts (about 3 s) before reaching the DLQ; harmless, not worth a custom classifier. Any other exception (DB or Redis down) takes the same retry path.
- **Unknown type or version:** handled by `ProjectionHandler` (log, no-op); the listener then marks it processed and acks. Not dead-lettered.
- **Order:** Redis check, commit, mark. Crash between commit and mark redelivers; the guarded upsert makes it a no-op. A Redis error is never swallowed, so the check is never skipped (listener fails, retries, dead-letters).
- **TTL 7 days:** longer than any plausible broker outage or outbox retry; the `occurredAt` guard is the backstop beyond it.
- **Health:** Boot's Rabbit and Redis indicators join automatically through `HealthController`'s aggregated status; the `topology` indicator keeps the service DOWN until the listener container is running, which is after RabbitAdmin has declared the queue and binding. There is no broker call that checks the binding itself, so "container running" is the proxy for it.
- **Switch for offline tests:** `app.messaging.enabled` (default true) rather than mocking beans.

## What each test proves
- `EventListenerTest`: handle then mark in that order; an already-processed event is skipped with no handler call and no mark; a handler failure is rethrown and not marked; a Redis failure on the check is rethrown and nothing is applied; seven malformed bodies are rejected without requeue.
- `RedisProcessedEventStoreTest` (real Redis): unknown id is not processed; mark sets `processed:{id}` with a 7 day TTL; marking twice is harmless.
- `TopologyHealthIndicatorTest`: DOWN if the queue is missing, no container runs, there are no containers or the broker throws; UP only when the queue exists and a container runs.
- `EventPipelineTest` (RabbitMQ + Redis + PostgreSQL): exchange, queue and DLQ exist; duplicate message changes the table once; submitted, step_approved, approved end with a closed row; malformed body arrives in the DLQ intact; unknown type is acked, not dead-lettered; two transient failures are retried then succeed (3 calls); a persistent failure dead-letters after exactly 3 calls and is not marked in Redis; `/notify/health` is 200 `{"status":"UP"}` and contains `rabbit`, `redis` and `topology`.

## Review this hardest
- `EventListener.onMessage`: the order of check, handle, mark, and that nothing catches a Redis or DB exception.
- `application.yml` retry block: confirm `max-retries: 2` really means 3 attempts (`persistentFailureIsDeadLetteredAfterThreeAttemptsAndNotMarked` asserts exactly 3 invocations).
- `TopologyHealthIndicator`: it does not read the binding itself, only that the queue exists and the consumer runs.
- A consumer-restart gap: a message published while the queue did not yet exist is lost (contract known limit); the Compose `depends_on` the lead adds is what prevents it.

- A body with no `version` deserialises to 0 and is acked as an unsupported version rather than dead-lettered as malformed; a known v1 type with a null `payload` is retried 3 times, then dead-lettered (review notes).
