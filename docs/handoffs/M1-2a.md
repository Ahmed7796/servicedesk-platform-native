## Decisions made
- A `PublishRejectedException` leaves the row unsent, the batch continues, and the row is retried next batch (Ahmed's decision; no parking). Alternative: count failures and park a row after N tries.
- The dispatcher does not log. Application has no logging package, so rejected rows come back in `DispatchResult.Rejected` and the caller logs them. Alternative: add `Microsoft.Extensions.Logging.Abstractions` to Application.
- After a confirm the row is saved with `CancellationToken.None`, so a shutdown does not skip the save and cause a duplicate. `ThrowIfCancellationRequested` runs before each following row.
- Rows are saved one at a time. A crash re-sends at most one message. Alternative: one save per batch, which is cheaper but re-sends up to 50.
- `RabbitMqOptions` is a record built by a static method, not `IOptions<T>` binding, so the error messages can name the environment variable.

## Review this hardest
- `OutboxDispatcher`: the order of `PublishAsync`, `MarkSent`, `SaveAsync`, and the two catch blocks (unavailable returns, rejected continues).
- Ordering (`OccurredAt`, then `Id`) and `Take(limit)` live in the EF query in `OutboxDispatchStore`. No unit test can check them; they are verified only in compose.
- The fakes in `OutboxDispatcherTests` mimic the real store (unsent only, at most `limit`). If they drift from the EF query the tests would still pass.

### Known limits
- If 50 or more of the oldest unsent rows are permanently rejected, they fill every batch and block everything behind them. Accepted for the demo.
- One API instance is assumed. Two instances could publish the same row twice; consumers de-duplicate on `eventId` (rule 5). No row locking.
- Delivery is at-least-once: a crash between the broker confirm and the save re-sends that row.

## Java to C# notes (C# tasks only)
- `IEventBroker` and `IOutboxDispatchStore` in `Application` with implementations in `Infrastructure` are like a Java port interface in the service layer with an adapter class in the infrastructure package. Different from Spring: nothing is wired until `services.AddScoped<...>()` is called; there is no component scanning, which is why nothing runs yet.
- `class OutboxDispatcher(IOutboxDispatchStore store, IEventBroker broker, TimeProvider clock)` is a primary constructor, like constructor injection with `final` fields. The parameters are usable in every method but are not fields you can name with `this.`.
- `TimeProvider` is like an injectable `java.time.Clock`. Tests use `Substitute.For<TimeProvider>()` (NSubstitute, like Mockito) to fix the time.
- `sealed record DispatchResult(int Published, IReadOnlyList<OutboxMessage> Rejected, bool BrokerUnavailable)` is like a Java `record`; `RabbitMqOptions` is also a record. Careful: a record compares members with their own `Equals`, and `List<T>` compares by reference. So two `DispatchResult`s with equal list contents are not equal, unlike Java's `record` with `List.equals`. Nothing here relies on that equality; tests read the members.
- `class BrokerUnavailableException(string message, Exception? inner = null) : Exception(message, inner)` is a one-line exception with a primary constructor and a default argument. Java has no default arguments, so it would be two constructors. C# has no checked exceptions: the `<exception>` doc comments are the only contract, and callers are not forced to catch.
- `catch (BrokerUnavailableException)` then `catch (PublishRejectedException)` after one `try` works like multi-catch in order; the first matching block wins.
- `CancellationToken` is like passing an `Interrupt`-aware context by hand. Nothing is cancelled unless each call checks it, hence `ct.ThrowIfCancellationRequested()`. `CancellationToken.None` is "never cancelled"; `CanBeCanceled` is false for it, which the test uses to prove the save ignored cancellation.
- `Task` and `await` are like `CompletableFuture`, but `await` does not block a thread; the method resumes later. `Task<IReadOnlyList<T>>` is `CompletableFuture<List<T>>` with a read-only view.
- Tracked entities: `GetUnsentAsync` returns entities that `AppDbContext` tracks. `MarkSent` changes a field and `SaveChangesAsync` writes it, like changing a managed JPA entity inside a `@Transactional` method and letting the flush write it. There is no annotation: the DbContext, scoped per DI scope, is the unit of work.
- `[Theory]` with `[InlineData]` is JUnit 5 `@ParameterizedTest` with `@CsvSource`. Hand-written fakes (`FakeStore`, `FakeBroker`) are used instead of mocks where call order matters: they record into one shared list, which Mockito would need `InOrder` for.
- `Assert.ThrowsAnyAsync<OperationCanceledException>` accepts subclasses (like `assertThrows`); `Assert.Throws<T>` needs the exact type.
- Collection expressions `[a, b]` and `[.. xs, y]` are like `List.of(a, b)` and a spread; `[]` is an empty list.
